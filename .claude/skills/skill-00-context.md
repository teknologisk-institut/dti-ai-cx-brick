# Skill 00: Shared Context

Load this file before every skill. It defines shared terminology, data layout, the skill-based pipeline, and rules that apply across all skills.

## Terminology

The same physical area is referred to differently across data sources. Always normalise to **"room"** in the building model:

| Term | Source | Meaning |
|------|--------|---------|
| **Room** | Building model (canonical) | Physical space — use this everywhere |
| **Space** | IFC/BIM (`IfcSpace`) | = Room |
| **Zone** | CTS/BMS pointlist (e.g. `Z_101`) | An HVAC zone, identified by zone ID; a zone is matched to one or more rooms by the building's confirmed rule (`zone-rooms.json`) |

IFC spaces become **rooms** in spatial-hierarchy.json; pointlist zones stay zones there, each with its rooms
(`zones[].roomIds`), status and evidence (see the point-mapping skill, "Zone↔room matching").

## Data Layout

Each building has raw inputs, generated inputs (built by tools), and TTL outputs:

```
data/{buildingId}/
├── inputs/
│   ├── {buildingId}_pointlist.csv    ← raw: BMS alarm/config export
│   ├── *.ifc                         ← raw: IFC/BIM model
│   ├── objects.json                  ← raw: TimescaleDB/BACnet object registry
│   ├── pointlist-plants.csv          ← generated by split-pointlist-csv.ts
│   ├── pointlist-zones.csv           ← generated by split-pointlist-csv.ts
│   ├── ifc-spatial.json              ← generated by build-spatial-hierarchy.py (IFC facts only)
│   ├── spatial-hierarchy.json        ← generated by match-zone-rooms.ts
│   ├── plant-point-mapping.json      ← generated by map-plant-points.ts
│   ├── zone-point-mapping.json       ← generated by map-zone-points.ts
│   ├── building-connections.json     ← generated by update-connections.ts
│   └── equipment-inventory.json      ← generated by update-equipment.ts
├── zone-rooms.json                   ← confirmed zone↔room rule, source rows, checks, decisions (write-zone-rooms.ts)
├── outputs/
│   └── *.ttl                         ← generated by generate-ttl.ts
└── images/
    ├── plants_overview/              ← the BMS's plant-overview tabs
    ├── rooms_overview/               ← the BMS's zone-overview tabs
    ├── floorplans/                   ← one image per floor/wing section
    ├── plants/                       ← one image per plant
    └── rooms/                        ← one image per zone
```

### Source data files

These five generated JSON files are the single source of truth for the building model. Each is produced by a specific tool and later enriched with `brickClass` by classify-all.ts.

| File | Produced by | Contains |
|------|-------------|----------|
| `spatial-hierarchy.json` | `match-zone-rooms.ts` | Building, floors (`level-{n}` ids, `level-m{n}` below level 0), rooms (`source` `ifc` or `documents`) and zone-centred `zones[]` (status `matched`/`created`/`unlinked`, `roomIds`, `floorId`, name, use group, evidence); from `ifc-spatial.json` + the zone list + `zone-rooms.json` |
| `plant-point-mapping.json` | `map-plant-points.ts` (bacnet: `map-bacnet-points.ts`) | Plants with points, TSDB/BACnet linkage, semantic meaning; bacnet also `devices` (controller-wide device points) and each plant's `groupedBy` (the rule that produced it) |
| `zone-point-mapping.json` | `map-zone-points.ts` (bacnet: `map-bacnet-points.ts`) | Zones with points, TSDB/BACnet linkage, semantic meaning (bacnet: `groupedBy`) |
| `building-connections.json` | `update-connections.ts` | Topology: plant↔zone feeds, plant↔plant serves, hierarchy |
| `equipment-inventory.json` | `update-equipment.ts` | Equipment per plant/zone: point-list items (`--bms`, source `bms`) and image items with ductPath and systemType |

## Skill-Based Pipeline

The pipeline runs as a sequence of skills, each with its own tool(s). Load the relevant skill's SKILL.md before starting work.

```
Step 0 — Inventory (building profile; skill: point-mapping)
  ├── agent lists data/{b}/, proposes dataShape ("timeseries" | "bacnet") + inputs
  │   (paths relative to data/{b}/) with the evidence for each field
  ├── agent drafts timeseries pointListFormat (delimiter, columns, nullValue, skipRows) then naming, the
  │   id grammar (timeseries zoneId, pointToken, ...; bacnet objectNames — device roles, prefix
  │   cleanup, ordered object rules, merge rules — and pointParts; both separator and plantToken)
  ├── when the profile declares images, the agent also drafts `bmsScreens` (the building's screen guide,
  │   `data/{b}/notes/bms-screens.md`), `notes`, `feedsSources` and, with installation IFCs,
  │   `naming.ifcSystemPlant` (IFC system names vs the plant list); the human confirms them with the rest
  │   of the profile (HITL below)
  ├── drafting the screen guide: open a few images of each declared kind first; the guide has these
  │   sections, which the image skills look up by heading: `## BMS and screen size` (BMS product, screen
  │   resolution), `## Plant overview screens` (what the overview tabs show), `## Floorplans` (plant
  │   buttons, title-bar floor names, button size, views), `## Room schematics` (header fields, where the
  │   parent-plant reference and labels sit, crop regions), `## Plant schematics` (header fields, the
  │   heat-recovery block's name, crop regions, corner→stream layout), `## Equipment id → type` (screen
  │   id → vocabulary type, guidance); write "not used by this building" under a heading whose kind is
  │   absent. `notes` holds pitfalls found later and may start as an empty file. A building that already
  │   has a profile gets these fields by re-writing it (`write-building-profile.ts <b> --force`)
  ├── HITL: human confirms the route, the input list, the pointListFormat (timeseries) and the naming
  │   evidence (bacnet: each object rule with its counts and sample splits, skips, unplaced shapes)
  ├── profile `inputs` keys (authority: tools/lib/building-profile.ts `ProfileInputs`): pointList +
  │   tsdbObjects (timeseries, required), devices + bacnetObjects (bacnet, required), architectureIfc,
  │   installationIfcs (array), images.{plants,rooms,floorplans,plantsOverview,roomsOverview},
  │   docs.{abbreviations,functionDescriptions,zoneMatrix}; image-related profile keys: `bmsScreens`,
  │   `notes`, `feedsSources` (floorplanColours | roomSchematicPlantButton | installationIfc),
  │   `naming.ifcSystemPlant`
  ├── write-building-profile.ts → data/{b}/building-config.json (validated, schemaVersion 2)
  └── pipeline-status.ts        → which of steps 0–6 apply / are done for this building
  Dictionary step (point-mapping skill, "HITL touchpoint 2", moment 1) comes next, BEFORE point mapping:
  agent drafts data/{b}/point-dictionary.draft.json (one shape: tokens, suffixes, words, units, overrides,
  plantTokens, plantOverrides) from the docs and point list through write-point-dictionary-entry.ts;
  review-dictionary-draft.ts lists what needs the human (word discovery, coverage per point, word clashes, ...); `promote` writes
  point-dictionary.json once nothing is open.
  The profile-aware tools (map-points and the mappers, update-equipment,
  classify-all, generate-ttl, validate-refs, pipeline-status) stop with
  "no building profile — run the inventory step (see point-mapping skill)"
  if the profile is missing.

Step 1 — Parse raw inputs (no skill needed)
  ├── split-pointlist-csv.ts     → pointlist-plants.csv, pointlist-zones.csv (timeseries only):
  │     npx ts-node tools/split-pointlist-csv.ts {buildingId}
  └── build-spatial-hierarchy.py --building <id> → ifc-spatial.json (IFC facts only: building, every
        storey, every space, and room → feeding plants when the profile lists installation IFCs;
        no filtering, numbering or zones)

Step 2 — Point mapping (skill: point-mapping)
  └── map-points.ts → dispatches on dataShape:
        timeseries: split-pointlist-csv → map-plant-points → map-zone-points
        bacnet:     map-bacnet-points
      (writes plant-point-mapping.json + zone-point-mapping.json)
  Joins CSV pointlists with objects.json (timeseries) or walks devices.csv + the object files with
  the profile's naming.objectNames (bacnet: every object is a plant/zone point, a device point of
  its controller, or skipped by a counted rule), groups by parent → flat points with id parts
  (idParts), label (semanticMeaning) + TSDB/BACnet reference
  Loop-back after mapping (moment 2): unresolved tokens/suffixes (mapping summary), uncovered words and
  points without role or quantity go through `write-point-dictionary-entry.ts init <b> --gaps`, the same
  review and promotion, then mapper `--force` (reviewed points/plants carried over) + classify-all.ts.
  After step 4, the same loop-back runs the post-image stream check (review --equipment).

Step 2a — Equipment items from the point list (skill: equipment-inventory; both routes)
  └── update-equipment.ts <b> --bms → equipment-inventory.json
  For every plant and zone in the mapping files: a point whose token entry has an equipmentType
  creates an item; runs after mapping and before image extraction, independent of images; idempotent;
  never overwrites image fields. pipeline-status shows it as done once it covered the current mapping.

Step 2b — Zone↔room matching (skill: point-mapping, "Zone↔room matching"; after point mapping, because
  it reads the zones from zone-point-mapping.json)
  ├── agent drafts the rule and reads the second sources → write-zone-rooms.ts → data/{b}/zone-rooms.json
  ├── match-zone-rooms.ts <b> --review → HITL: rule, check flags, disagreements, no-room, rule-only
  └── match-zone-rooms.ts <b> [--force] → spatial-hierarchy.json (zone-centred; floors, rooms, zones)
  Re-run after step 3 when the feeds source (building-connections.json) appears.

Step 3 — Building connections (skill: building-connections)
  └── update-connections.ts → building-connections.json
  Extracts topology from BMS images: plant↔zone feeds (by the profile's `feedsSources`),
  plant↔plant serves, plant hierarchy

Step 4 — Equipment inventory (skill: equipment-inventory)
  ├── update-equipment.ts         → equipment-inventory.json
  └── run-equipment-extraction.ts   (batch wrapper, uses claude -p)
      (NOTE: run-equipment-extraction.ts is a headless batch runner with no human present: it
      writes equipment without `ductPath`, `ductOrientation` or `medium` and skips plants that
      already have a `ductOrientation`; touchpoint 1 and the medium confirmation follow
      interactively.)
  Extracts fans, coils, dampers, valves, sensors from
  plant + room schematic images, with ductPath positioning; image writes enrich the
  point-list items of step 2a and add devices that have no points

Step 5 — Brick classification (skill: brick-assign)
  ├── classify-all.ts → writes brickClass into all source data files
  ├── assign-brick.ts → single-entity override
  ├── group-low-confidence.ts → stdout — HITL touchpoint 3 grouping of the points to review
  │     (needsReview, confidence:'low' or a trade-off flag) by flag kinds and deciding entries
  │     (read-only, regenerates fresh every run)
  └── compare-classes-by-cause.ts / apply-class-verdicts.ts → after a dictionary change: class
        changes grouped by cause, the human's better/worse verdicts applied to reviewed points
  Points and plants are classified from parts: each point's role, quantity, medium, stream, ...
  is decided by its first source in the order override → image ductPath → id suffix →
  description words → id token → unit/state texts → plant type, all from the building's
  dictionary; brick-classification-index.json's class tags pick the class. Flags (trade-off,
  tie, role fallback, ...) are written onto the point; every point tag reaches the TTL
  (brick:hasTag). Classes are written directly into the data files (in-place)

Step 6 — Generate TTL (skills: brick-relationships + generate-ttl)
  ├── generate-ttl.ts → outputs/building.ttl
  └── validate-ttl.ts → validation report
  brick-relationships defines how entities connect (triples),
  generate-ttl assembles the final Turtle file for GraphDB
  Steps 5–6 need inputs/spatial-hierarchy.json (step 2b): classify-all and generate-ttl stop without it, so
  a building without an architecture IFC cannot produce a TTL yet

Step 7 — Query (no skill needed)
  └── audit-classes.ts     → stdout — generic-classed points whose Danish desc implies a more-specific class
```

### Building-profile tools

- `write-building-profile.ts` — `echo '<json>' | npx ts-node tools/write-building-profile.ts <b> [--force]`
  validates and writes `data/{b}/building-config.json`; `--validate` re-checks an existing profile.
  Missing declared input paths are warnings, structural problems are errors (exit 1). For timeseries it also
  runs a data check against the declared point list: zone/plant row counts per `naming.zoneId` (0 zone rows or
  every row is a warning), rows skipped per `skipRows` rule, null cells, and a missing `pointListFormat` column
  (error). For bacnet it runs the same kind of check against `devices.csv` and the object files: devices per
  device rule (a device with an object file and no role is an error), per object rule the objects placed,
  parents and three sample splits, skips per rule, merges, unplaced objects by name shape, copies of one
  name on several controllers (with differing values), distinct objects that would share one id (kept apart
  with a type-instance, else device-type-instance, suffix; the mapper refuses duplicate ids), a rule
  matching nothing (warning) and grammar plants with no `plantTokens`/`plantOverrides` entry (warning).
- `map-points.ts` — `npx ts-node tools/map-points.ts <b> [--force]`; step 2 dispatcher on `dataShape`.
- `pipeline-status.ts` — `npx ts-node tools/pipeline-status.ts <b>`; read-only, steps 0–6, each
  applies / skipped (reason) / done. `done` means the output exists — there is no staleness check, except
  for the point-list equipment items (step 2a), done when `equipment-inventory.json` `meta.bmsPass` matches the
  current plant mapping's `generatedAt`. After the step rows it prints two review lines computed from
  `equipment-inventory.json` (duct direction confirmed on N of M plants; equipment medium on N of M plant
  equipment items); they replace any hand-kept rollout state.

`update-equipment.ts`, `classify-all.ts` (the id grammar per route), `generate-ttl.ts`
(BACnet refs when `dataShape` is bacnet; devices from `inputs.devices`) and `validate-refs.ts` branch on
`profile.dataShape`, not on building id or file probes.

### Timeseries vs bacnet, stage by stage

The steps above are the same stages for every building, but the tool and behavior at each stage
depends on the profile's `dataShape`: `timeseries` is a BMS pointlist CSV + a separate TimescaleDB
object registry; `bacnet` is a BACnet device scrape with no CSV/TSDB split. Tools read `dataShape`
from the building profile (Step 0). Each skill's own SKILL.md has the full detail; this table is the
map of where to look, not a replacement for reading them.

| Stage | Skill | timeseries | bacnet |
|---|---|---|---|
| 0. Inventory | point-mapping | Profile lists the `*_pointlist.csv` and `objects.json` | Profile lists `devices.csv` and the object CSVs folder, and holds the object-name grammar `naming.objectNames` (device roles from `devices.csv` columns, prefix cleanup, ordered object rules, merge rules) and `naming.separator` |
| 1. Parse raw inputs | *(none)* | `split-pointlist-csv.ts` splits the pointlist → plants/zones CSVs, then `build-spatial-hierarchy.py` (architecture IFC → `ifc-spatial.json`) | No CSV split — BACnet device/object CSVs are the raw input directly. `build-spatial-hierarchy.py` runs against the architecture IFC (and the **ventilation IFC**, profile `installationIfcs`, for room → feeding plants; also used in stage 3). |
| 2. Point mapping | point-mapping | `map-points.ts` runs `map-plant-points.ts` + `map-zone-points.ts` — join pointlist CSV rows against `objects.json`'s TSDB registry | `map-points.ts` runs `map-bacnet-points.ts` — one tool, both outputs in one pass; a generic device/object walker: each device's role and each object's plant, zone or skip come from `naming.objectNames`, objects no rule places become **device points** of their controller (`plant-point-mapping.json` `devices`); splits each point part with `naming.pointParts` and reads the same one-shape dictionary (object-name is already the reference id, no separate join). Vendor registers are ordinary dictionary entries; there is no vendor table. **Do not reuse another building's abbreviation tables** — the same prefix can mean something else (e.g. `SP` = Setpunkt in one, Spjæld/damper in another). |
| 2b. Zone↔room matching | point-mapping | `match-zone-rooms.ts` — same tool and mechanism for both shapes: zones from `zone-point-mapping.json`, the building's rule and sources in `zone-rooms.json` | (same; a building with installation IFCs and `building-connections.json` also gets the feeds check) |
| 3. Building connections | building-connections | By `feedsSources` (the method follows the building's sources, not its data shape): `floorplanColours` reads plant→zone `feeds` from floorplan image colors (plant↔zone color-coding); `roomSchematicPlantButton` from the room schematic's feeding-plant button; any image source plus `installationIfc` → also derived independently from the installation IFC, then reconciled via `reconcile-feeds-ifc.py` (dual-source) | By `feedsSources` (same) |
| 4. Equipment inventory | equipment-inventory | `update-equipment.ts --bms` (step 2a, before the images) writes every plant's and zone's point-list items: the type is the `equipmentType` of the point's token entry in the dictionary (a token without one creates no item), the item id the point abbreviation; image writes enrich them | Same rule and pass; the item id is the point's `{token}{number}` from its id parts; an item whose id is the plant's own trailing device part is not created (self-device) |
| — ductPath/`ductOrientation` HITL (touchpoint 1) | equipment-inventory | Mechanism identical for both shapes. | (same) |
| — equipment `medium` HITL | equipment-inventory | Mechanism identical for both shapes; merged 2026-08-20. | (same) |
| 5. Brick classification | brick-assign | One mechanism for both shapes: points and plants classified from parts (dictionary entries per source, fixed source order, Brick class tags pick the class). Plants: plant override → plant-token entry + `plantName` words + parent plant, image equipment composition as check / tie-breaker. Points get the image `ductPath` source (level 2) and symbol unit entries | Same mechanism, sources and dictionary shape (no vendor-specific source). Points add BACnet state texts (word entries); units come from the generic BACnet unit-name table (`no-units` counts as no unit). Device points are classified the same way, with no plant tags; their host is their controller. `equipment-inventory.json`/`building-connections.json` are optional: without them plants have no composition check and points no image `ductPath`. |
| 6. Generate TTL | brick-relationships + generate-ttl | `objectType` reaches the TTL via `ref:TimeseriesReference` — no `bacnet:object-type` triples emitted | `objectType` also reaches the TTL as a `bacnet:object-type` triple (BACnet refs when `dataShape` is bacnet; devices from `inputs.devices`). This is why `validate-ttl.ts`'s binary/Sensor guardrail sees bacnet buildings but is **blind to timeseries** — the classify-all.ts-level guard (`isBinarySensorMismatch`) is the one that covers both. |
| 7. Query | *(none)* | Same tools, same behavior — building-agnostic, keyed by `buildingId` argument | (same) |

A building's shape is its profile's `dataShape`; review progress: `npx ts-node tools/pipeline-status.ts {buildingId}`.

### Mediums
Use only: `air`, `hotWater`, `chilledWater`, `electricity`, `steam`, `water`

### Example: Context-Dependent Prefixes

One token can mean different things in a zone and in a plant; the building's dictionary decides
(`point-dictionary.json` keeps token entries per context: `tokens.zone`, `tokens.plant`, `tokens.any`).
In `DEMO-TS` each token is used in one context only:

| Token | Context | Entry gives | Class |
|--------|---------|-------------|-------|
| `TR` | zone (`Z_101`) | `tokens.zone.TR`: [Zone, Air, Temperature, Sensor] | `Zone_Air_Temperature_Sensor` |
| `TI` | plant (`VE01`) | `tokens.plant.TI`: [Supply, Air, Temperature, Sensor] | `Supply_Air_Temperature_Sensor` |
| `TF` | plant (`VA07`) | `tokens.plant.TF`: [Supply, Water, Temperature, Sensor]; Hot comes from the parent plant's class tags (`Hot_Water_System`) | `Supply_Hot_Water_Temperature_Sensor` with no equipment or on a pump; `Leaving_Hot_Water_Temperature_Sensor` on an exchanger or meter (the water host routing) |

## Image Processing Rules

Applies when the profile declares `inputs.images` (otherwise skip this section); read the building's screen guide (`bmsScreens`) and `notes` first.

**CRITICAL: Save after EACH image** to prevent data loss.

- Process **one image at a time**
- Save immediately after each image
- Use brief confirmations only:

```
Processing Z_101... ✓ (2 points: TR1, TR1_SP)
Processing Z_102... ✓ (2 points: TR1, TR1_SP)
```

**Never** repeat previously found data in confirmations. The data is saved — don't waste tokens.

## BMS Image Reading Protocol (resolution + cross-check)

Applies when the profile declares `inputs.images` (otherwise skip this section); read the building's screen guide (`bmsScreens`) and `notes` first.

BMS screenshots are dense. Most labels/values (plant buttons, sensor IDs,
setpoints) are **below readable size at full frame** — a full-frame read mislabels or
wrongly concludes data is "absent." Follow this protocol for every image:

1. **Crop-first — never read from the full frame.** A full-frame view is for orientation
   only. Read every label/value from an upscaled crop:
   ```
   python tools/crop-image.py <image> --region NAME=x0,y0,x1,y1 --scale 3
   python tools/crop-image.py <image> --skeleton          # full-width band, for the step below
   ```
   **Never record a value, and never conclude a field is "absent," from a full-frame read.**
   If a region is unreadable even when cropped, mark it `low`/`unreadable` — don't guess.

2. **ductPath is geometric, not a label — decide it from a skeleton pass, not a band crop.**
   ductPath depends on an element's position relative to the heat-recovery block (the block
   between the two duct lines that shows the recovery efficiency), so a band crop read in
   isolation cannot assign it. First take a `--skeleton` crop
   showing both duct lines + the HR block + flow arrows; fix the HR x-position and the two
   line y's. Then label each of the four corners with its stream from the skeleton geometry and the flow
   arrows; the layout differs per screen.
   Cross-check the independent signals present: the **supply/extract side marker** (if the confirmed
   profile declares `naming.airDirectionMarker`) and the **temperature gradient** (intake cold →
   supply warm; return room-temp → exhaust cooled). The geometry and every signal present must agree. State the proposed
   legend and this reasoning to the human for confirmation **before** writing any equipment's
   `ductPath` — see `equipment-inventory/SKILL.md`'s "Duct/pipe orientation confirmation" section
   for the full workflow (this step's reading method is unchanged, only the confirm-before-write
   gate is new). After extraction:
   ```
   npx ts-node tools/validate-ductpath.ts {buildingId}   # flags side-marker↔ductPath mismatches
   ```

3. **Plant→zone (feeds) with an installation IFC is dual-source, reconciled.** Where the profile's
   `feedsSources` lists `installationIfc` together with an image source (`floorplanColours`, or
   `roomSchematicPlantButton`: the room schematic names the feeding plant, e.g. a button carrying the
   plant's id), the IFC derives the same independently. Reconcile, don't trust one:
   ```
   python tools/reconcile-feeds-ifc.py {buildingId} <vent_ifc>   # match / IFC-only / image-only
   ```

4. **Validate every id against ground truth.** Zone ids against `spatial-hierarchy.json`
   `zones[].id`, plant ids against `plant-point-mapping.json`. An unknown id means a misread —
   re-crop and re-read; never accept or invent one.

## Danish Language Awareness

Applies when the profile declares `inputs.images` (otherwise skip this section); read the building's screen guide (`bmsScreens`) and `notes` first.

BMS images contain Danish text. The three special characters **ø**, **æ**, **å**
are critical and must be read correctly — misreading them produces nonsense descriptions
or wrong plant IDs that match no plant, or the wrong one.

**High-risk confusions in BMS images:**

| Character | Common misread | Example | Impact |
|-----------|---------------|---------|--------|
| `ø` | `a`, `o`, or `0` (zero) | `pumpebrønd` → `pumpebrand` | Wrong meaning (pump well vs pump fire) |
| `ø` in IDs | `0` (zero) or `O` | `VEØ1` → `VE01` | ID matches no plant, or the wrong one |
| `å` | `a` or `aa` | `Påluftning` → `Paluftning` | Description corruption |
| `æ` | `ae` | `Anlæg` → `Anlaeg` | Usually recoverable |

**Rules when reading images:**
1. When a description seems semantically wrong, consider whether `ø`/`æ`/`å` was misread
2. Plant IDs containing `Ø` (e.g. `VEØ1`) — always cross-check
   against the known plant list from plant-point-mapping.json to confirm the ID
3. `pumpebrønd` = pump well/sump — not related to fire (`brand`)
4. `Øst` = East, `Vest` = West — directional wing labels, not German words
5. `Påluftning` = supply air intake — the `å` is not a typo

**Recovery:** If an extracted description or ID doesn't match anything in the data files,
re-read the image specifically looking for `ø`/`æ`/`å` before flagging as unknown.

## Brick (nightly) Class Conventions (apply across skills)

- **No deprecated classes.** The model uses only non-deprecated Brick (nightly) classes; `validate-ttl`
  errors on deprecated ones (its index excludes them). Spatial uses `rec:HVACZone` / `rec:Room`
  (not `brick:HVAC_Zone` / `brick:Room`).
- **Water Supply/Return vs Entering/Leaving is equipment-role-based, not medium-based** (2026-08-18,
  replaces the old medium-only rule): a loop's own pump/valve → `Supply_*`/`Return_*`; boundary-interface
  equipment (heat exchanger, chiller, meter) → `Leaving_*`/`Entering_*` (supply/fremløb *leaves* the
  boundary, return/returløb *enters* it — opposite of a load/coil frame); Controller-hosted points (no
  physical-equipment owner) → no directional tag. Air is unaffected — Brick has no `Entering_Air_*`/
  `Leaving_Air_*` classes, so Air-medium points still use the existing ductPath-based Supply/Return/
  Exhaust/Intake rule unchanged. DHW has no `Supply_`/`Return_` variant at all (only `Entering_`/
  `Leaving_`), even when hosted by loop equipment. See the **brick-assign** skill for the full mapping;
  the routing algorithm (`pointHost` resolution) this depends on is `resolvePointHost` in `classify-all.ts`.
- **Zone-air temperature setpoint** is split by the point's tags — `Heating_` / `Cooling_` /
  `Effective_…_Zone_Air_Temperature_Setpoint` when its word or suffix entries give Heat, Cool or Effective,
  deadband → `Temperature_Deadband_Setpoint`, otherwise `Target_` (a generic convention).
- See the **brick-assign** skill ("Brick (nightly) conventions") for the full mapping. Validate output with
  `validate-ttl {id}` (structure) **and** `validate-refs {id}` (timeseries/BACnet ids vs the input files).

## Brick Ontology Reference

```
ontologies/Brick_nightly.ttl                ← raw schema, current source (do NOT load into context)
ontologies/brick-classification-index.json  ← compact class index for classification
ontologies/brick-relationship-index.json    ← compact relationship index for TTL generation
```

**Always use the index files — never the raw TTL.** The raw TTL is ~3MB and would consume too much context.
Both indexes are built from `Brick_nightly.ttl` (the nightly build for Brick 1.5.0, added on 2026-08-17).

Generate the indexes once (after downloading a new Brick_nightly.ttl):
```bash
npx ts-node tools/build-brick-classification-index.ts ontologies/Brick_nightly.ttl ontologies/brick-classification-index.json
npx ts-node tools/build-brick-relationship-index.ts ontologies/Brick_nightly.ttl ontologies/brick-relationship-index.json
```

The classification index includes both:
- **`brick:`** classes — equipment, points, systems, locations
- **`rec:`** classes — RealEstateCore spatial classes (Building, Floor, Room, Zone, Site...)

Always use underscores in `brick:` class names — `Air_Handling_Unit` not `AirHandlingUnit`.
`rec:` class names use CamelCase — `rec:Room`, `rec:BuildingStorey`, `rec:Office`.
